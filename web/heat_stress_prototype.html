Why Town-Level Data, Not District-Level (SHRAM)

SHRAM/EHI-N reports one risk number per district. A district can easily contain both a storm and a heatwave at the same time — which is exactly the flaw this project exists to fix. Below is a live example using this prototype's own data:

Both fall inside Udupi district — SHRAM would report one shared number for both. This prototype pulls each separately, which is why the two can (and do) show different risk levels here.

The Risk Calculation (WBGT-based)

We use the Australian Bureau of Meteorology's published outdoor WBGT approximation — a standard formula, not something invented for this project:

WBGT ≈ 0.567×T + 0.393×e + 3.94
where T = dry-bulb temperature (°C), e = water vapour pressure (from RH%)

Then we adjust for factors the raw formula doesn't capture:

FactorAdjustmentWhy
Labor type: Light+0°C effectiveLow metabolic heat generation
Labor type: Moderate+1°C effectiveSustained physical activity
Labor type: Heavy+2°C effectiveHigh internal heat generation (3–4x resting)
No water in last hour+1°C effectiveReduced evaporative cooling capacity
Exposure > 3 continuous hrsEscalation flagCumulative heat strain, even if instantaneous score is borderline

Honest Limitations (for Q&A)

  • No public individual-level dataset (worker + conditions + health outcome) exists for India's informal sector — we calibrate against official published thresholds (IMD, State Heat Action Plans) instead of claiming data we don't have.
  • This is a decision-support tool, not a medical device — it recommends when to rest and when to escalate; it does not diagnose.
  • The weather readings in this demo are preset per town to demonstrate the calculation logic and the town-vs-district distinction. Production would connect live OpenWeatherMap/IMD APIs and a Twilio (or equivalent) SMS/IVR gateway.
  • The regional-acclimatization ML layer (Phase 2) is intentionally not built into this prototype — it is a modest, clearly-scoped future enhancement, not the headline claim.
